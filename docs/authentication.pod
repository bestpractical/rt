=head1 RT Authentication

RT allows for several different ways to authenticate users including an
internal user management system and a number of ways to integrate with existing
authentication systems.

=head1 Internal Authentication

RT's native internal authentication system provides administration tools to
manage usernames and passwords.  If you plan to run your RT as a stand-alone
system and don't need to use accounts associated with any other system, this
may be all you need.  The administration pages under Admin → Users
provide new user creation as well as password setting and control of RT's
privileged flag for existing users.

=head2 Secret Key

RT uses a secret key for cryptographic operations such as generating
password-reset tokens, MFA-reset tokens, and encrypting TOTP secrets stored
in the database. By default RT derives this from C<$DatabasePassword>, but
we recommend setting C<$SecretKey> to a dedicated long, random value in
F<RT_SiteConfig.pm>:

    Set($SecretKey, 'replace-with-a-long-random-string');

Using a dedicated secret avoids coupling application-level cryptography to
the database credential and makes key rotation straightforward.

=head2 Password Policy

RT enforces password complexity requirements through the
L<$PasswordPolicy|RT_Config/$PasswordPolicy> configuration option. This
replaces the older C<$MinimumPasswordLength> setting with a richer set of
checks.

The policy is a hash reference with up to three keys -- C<Default>,
C<Privileged>, and C<Unprivileged> -- each containing a policy hash. When a
user sets or changes a password, RT resolves the effective policy by checking
group policies first, then the user-type-specific key, then C<Default>, and
finally a built-in fallback of C<< MinLength => 5 >>.

Available policy fields:

=over 4

=item C<MinLength> - Minimum password length (0 to disable)

=item C<RequireUpper> - Require at least one uppercase letter

=item C<RequireLower> - Require at least one lowercase letter

=item C<RequireDigit> - Require at least one digit

=item C<RequireSymbol> - Require at least one non-alphanumeric character

=item C<NoUsername> - Password must not contain the username

=back

Example configuration with different requirements for privileged and
unprivileged users:

    Set($PasswordPolicy, {
        Default => {
            MinLength => 5,
        },
        Privileged => {
            MinLength     => 10,
            RequireUpper  => 1,
            RequireLower  => 1,
            RequireDigit  => 1,
            NoUsername    => 1,
        },
        Unprivileged => {
            MinLength => 8,
        },
    });

=head3 Per-Group Password Policies

Individual user-defined groups can have their own password policy, configured
via Admin -> Groups -> [Group] -> Password Policy. When a user belongs to
multiple groups that each define a policy, the most restrictive settings
across all groups are merged (highest C<MinLength> wins; any boolean
requirement wins if any group enables it).

Group policies take precedence over the global C<$PasswordPolicy> keys.

=head2 Self-Service Password Reset

RT includes a self-service password reset flow that allows users to request a
reset link via email. When enabled, a "Forgot your password?" link appears on
the login page. Users enter their email address, and if a matching account is
found, RT emails a time-limited link that allows them to set a new password.

Administrators can also send reset emails from the user admin page
(Admin -> Users -> [User] -> Modify), which is useful for onboarding new
users or unlocking accounts.

The reset flow uses the C<PasswordReset> template for emails. You can
customize the wording by editing this template under Admin -> Global ->
Templates.

=head3 Configuration

The following options control the reset flow. All are documented in detail
in L<RT_Config>.

=over 4

=item C<$DisableResetPasswordOnLogin>

Hides the "Forgot your password?" link on the login page and blocks the
self-service request page. Admins can still send reset emails from the user
admin page. Default: off.

=item C<$ResetLinkExpirySeconds>

How long a reset link remains valid. Default: 4 hours.

=item C<$ResetRequestCooldown>

Minimum seconds between consecutive reset emails for the same user,
preventing abuse. Default: 300 (5 minutes).

=item C<$HidePasswordResetErrors>

When enabled, all outcomes (user not found, disabled, etc.) show the same
generic success message, preventing user enumeration. Errors are still
logged. Default: on.

=item C<$ResetPasswordFromAddress>

Overrides the From address on reset emails. When unset, C<$CorrespondAddress>
is used.

=item C<$ResetPasswordAllowUsersWithoutPassword>

Allows users who have an RT account but no password to use the reset flow.
Default: off.

=item C<$ResetPasswordCreateNewUserAndSetPassword>

Allows visitors with unknown email addresses to create new accounts via the
reset page. B<Only enable this on non-public RT instances.> Default: off.

=item C<$ResetPasswordCreateNewUserAsPrivileged>

When combined with the above, new accounts are created as privileged.
B<Use with extreme caution.> Default: off.

=back

=head2 Multi-Factor Authentication (MFA)

RT supports Time-based One-Time Password (TOTP) multi-factor authentication.
When enabled, users enroll by scanning a QR code with a standard
authenticator app (Google Authenticator, Authy, 1Password, etc.). After
enrollment, users are prompted for a 6-digit code after entering their
password on each login.

=head3 Requirements

MFA support requires additional Perl modules (C<Auth::GoogleAuth>,
C<Crypt::URandom>, C<CryptX>, C<Text::QRCode>) and
the C<libqrencode> system library.
Pass C<--enable-mfa> to F<configure> to include these dependencies:

    ./configure --enable-mfa [other options...]

Run C<make testdeps> after configuring to verify the modules are installed.

If the required modules are not installed, RT automatically sets
C<$DisableMFA> to true and all MFA functionality is hidden. You can also
explicitly disable MFA by setting C<$DisableMFA> to 1 in
F<RT_SiteConfig.pm>.

=head3 Configuring MFA Policy

MFA behavior is controlled by the C<$MFAPolicy> configuration option. Like
C<$PasswordPolicy>, it supports C<Default>, C<Privileged>, and
C<Unprivileged> keys:

    Set($MFAPolicy, {
        Privileged => {
            Mode  => 'Required',
            Drift => 0,
        },
    });

The C<Mode> field accepts three values:

=over 4

=item C<Off> - MFA is disabled (default)

=item C<Optional> - Users may enroll via Preferences -> About Me, but are not required to

=item C<Required> - Users must enroll on their next login and verify on every subsequent login

=back

The C<Drift> field controls clock-drift tolerance between the
authenticator device and the server. It is the number of 30-second
TOTP windows accepted on each side of the current one. Use C<0> for
the current window only (strictest), C<1> to also accept one window
before and after, and so on up to a maximum of C<5>.

=head3 Per-Group MFA Policies

Individual user-defined groups can have their own MFA policy, configured via
Admin -> Groups -> [Group] -> MFA Policy. When a user belongs to multiple
groups, the most restrictive mode wins (C<Required> > C<Optional> > C<Off>)
and the smallest C<Drift> wins.

Group policies take precedence over the global C<$MFAPolicy> keys.

=head3 User Experience

=over 4

=item *

B<Required, not yet enrolled>: After entering a correct password, the user
is redirected to an enrollment page showing a QR code and a base32 secret
for manual entry. The user must enter a valid 6-digit code from their
authenticator app to complete enrollment and log in.

=item *

B<Required, enrolled>: After entering a correct password, the user is
redirected to a verification page and must enter a valid TOTP code to
complete login.

=item *

B<Optional>: Enrolled users see MFA verification on login. Users can
enroll or disable MFA from Preferences -> About Me.

=back

If a user loses access to their authenticator app, a "Lost access to your
authenticator?" link on the verification page lets them request an MFA reset
email. The reset link clears their enrollment so they can set up a new
authenticator. The C<MFAReset> template controls the wording of this email.

Administrators can also clear a user's MFA enrollment from the user admin
page (Admin -> Users -> [User] -> Modify).

=head3 Failed-Attempt Lockout

To slow online TOTP brute-force attempts, RT counts consecutive failed
verifications on each user account. After five failed attempts the account
is locked out of MFA verification for fifteen minutes. The lockout is
recorded on the user record, so it persists across browser sessions and
cannot be reset by logging in again. While locked out, password
authentication for that user is also refused with the same generic error
message used for wrong passwords, so an attacker cannot probe lockout
state.

A successful TOTP verification clears the counter, as does any of the
existing MFA reset paths (self-service "Lost access" link, admin reset
on the user page, or the SystemUser-level C<ClearTOTPEnrollment>). The
counter also auto-clears the next time the user's verify page is
visited after the fifteen-minute window has elapsed.

=head3 MFA and External Authentication

MFA enforcement is bypassed for sessions authenticated via C<REMOTE_USER>
(C<$WebRemoteUserAuth>), since the external authentication system (e.g. a
SAML or Kerberos identity provider) is expected to handle its own
second-factor requirements. If the same user logs in with a password
(when C<$WebFallbackToRTLogin> is enabled), MFA is enforced normally.

=head3 MFA and REST APIs

REST 1.0 and REST 2.0 password-based logins are rejected when MFA is
required for the user, since there is no interactive way to complete the
TOTP challenge. API users should use L<token authentication|/Token
Authentication> instead, which bypasses MFA.

=head1 Token Authentication

Authentication tokens are typically used for accessing RT's REST APIs,
often L<RT::REST2>. To set up token access, first select an RT user
account you will use when accessing APIs and give that user account
appropriate rights to operate on tickets based on what you plan to do
(read ticket information, create tickets, update tickets, etc.).

You can then give that user the right ManageAuthTokens which will
add a new option in the menu Logged in as > Settings > AuthTokens.

When setting up token authentication, add the following directive to
your RT Apache configuration to allow RT to access the Authorization header.

    SetEnvIf Authorization "(.*)" HTTP_AUTHORIZATION=$1

Since tokens grant access on behalf of a user, RT prompts for a password
when a user is creating a token. However, if you have a mix of RT and
federated authentication, RT can't authenticate users via the federated
password system. For this case, you can explicitly disable the password
check with the C<$DisablePasswordForAuthToken> configuration option.

=head1 External Authentication

There are two primary types of external authentication: in one you type your
username and password into RT's login form, and in the other your web server
(such as Apache) handles authentication, often seamlessly, and tells RT the
user logged in.

Starting with RT 4.4, both of these options are supported by RT out of the
box, activated using different configuration options. The first is supported
by the L<RT::Authen::ExternalAuth> module. The second is activated using
the configuration option C<$WebRemoteUserAuth> along with some related
options. These two types may be used independently or together, and both
can fallback to RT's internal authentication.

If you are running a version of RT earlier than 4.4, you can install
L<RT::Authen::ExternalAuth|https://metacpan.org/pod/RT::Authen::ExternalAuth>
as an extension.

No matter what type of external authentication you use, RT still maintains user
records in its database that correspond to your external source.  This is
necessary so RT can link tickets, groups, rights, dashboards, etc. to users.

All that is necessary for integration with external authentication systems is a
shared username or email address.  However, in RT you may want to leverage
additional information from your external source.  Synchronization of users,
user data, and groups is provided by an extension named
L<RT::LDAPImport>.  It uses an external LDAP source, such an
OpenLDAP or Active Directory server, as the authoritative repository and keeps
RT up to date accordingly.  This can be used in tandem with any of the external
authentication options as it does not provide any authentication itself.

Note that if you start with L<Internal Authentication> and then switch to
L<External Authentication>, your original users will still have passwords in
the RT database. RT ignores these passwords when handling logins, but in some
cases RT may show a password box that would normally be hidden for external
authentication because it detects an existing password. To avoid this, you can
clear passwords in the Users table when you switch to external authentication.

=head2 Via your web server, aka C<$WebRemoteUserAuth>, aka C<REMOTE_USER>

This type of external authentication is built-in to RT and bypasses the RT
login form.  Instead, RT defers authentication to the web server which is
expected to set a C<REMOTE_USER> environment variable.  Upon a request, RT
checks the value of C<REMOTE_USER> against its internal database and logs in
the matched user.

It is often used to provide single sign-on (SSO) support via Apache modules
such as C<mod_auth_kerb> (to talk to Active Directory).  C<$WebRemoteUserAuth> is
widely used by organizations with existing authentication standards for web
services that leverage web server modules for central authentication services.
The flexibility of RT's C<$WebRemoteUserAuth> support means that it can be setup
with almost any authentication system.

In order to keep user data in sync, this type of external auth is almost always
used in combination with one or both of L<RT::Authen::ExternalAuth> and
L<RT::LDAPImport>.

=head3 Apache Configuration

When configuring Apache to protect RT, remember that the RT mail gateway
uses the web interface to upload the incoming email messages.  You will
thus need to provide an exception for the mail gateway endpoint.

An example of using LDAP authentication and HTTP Basic auth:

    <Location />
        Require valid-user
        AuthType Basic
        AuthName "RT access"
        AuthBasicProvider ldap
        AuthLDAPURL \
            "ldap://ldap.example.com/dc=example,dc=com"
    </Location>
    <Location /REST/1.0/NoAuth/mail-gateway>
        Require local
    </Location>

=head3 RT Configuration Options

All of the following options control the behavior of RT's built-in external
authentication which relies on the web server.  They are documented in detail
under the "Authorization and user configuration" section of L<RT_Config>
and you can read the documentation by running C<perldoc /opt/rt5/etc/RT_Config.pm>.

The list below is meant to make you aware of what's available.  You should read
the full documentation as described above.

=head4 C<$WebRemoteUserAuth>

Enables or disables RT's expectation that the web server will provide
authentication using the C<REMOTE_USER> environment variable.

=head4 C<$WebRemoteUserContinuous>

Check C<REMOTE_USER> on every request rather than the initial request.

When this is off, users will remain logged into RT even after C<REMOTE_USER> is
no longer provided.  This provides a separation of sessions, but it may not be
desirable in all cases.  For example, if a user logs out of the external
authentication system their RT session will remain active unless
C<$WebRemoteUserContinuous> is on.

=head4 C<$WebFallbackToRTLogin>

If true, allows internal logins as well as C<REMOTE_USER> by providing a login
form if external authentication fails. This is useful to provide local admin
access (usually as root) or self service access for people without external
user accounts.

=head4 C<$WebRemoteUserAutocreate>

Enables or disables auto-creation of RT users when a new C<REMOTE_USER> is
encountered.

=head4 C<$UserAutocreateDefaultsOnLogin>

Specifies the default properties of auto-created users.

=head4 C<$WebRemoteUserGecos>

Tells RT to compare C<REMOTE_USER> to the C<Gecos> field of RT users instead of
the C<Name> field.

=head2 Via RT's login form, aka RT::Authen::ExternalAuth

L<RT::Authen::ExternalAuth> provides authentication
B<using> RT's login form.  It can be configured to talk to an LDAP source (such
as Active Directory), an external database, or an SSO cookie.

The key difference between C<$WebRemoteUserAuth> and
L<RT::Authen::ExternalAuth> is the use of the RT login form and what
part of the system talks to your authentication source (your web
server vs. RT itself).

As noted above, for versions of RT before 4.4, you can install
L<RT::Authen::ExternalAuth|https://metacpan.org/pod/RT::Authen::ExternalAuth>
as an extension.

=head3 Info mode and Authentication mode

There are two modes of operation in L<RT::Authen::ExternalAuth>: info and auth.
Usually you want to configure both so that successfully authenticated users
also get their information pulled and updated from your external source.

Auth-only configurations are rare, and generally not as useful.

Info-only configurations are commonly setup in tandem with C<$WebRemoteUserAuth>.
This lets your web server handle authentication (usually for SSO) and
C<RT::Authen::ExternalAuth> ensures user data is updated every time someone
logs in.

=head2 RT::Extension::LDAPImport

L<RT::LDAPImport> provides no authentication, but
is useful alongside authentication because it provides user data and group
member synchronization from any LDAP source into RT.  It provides a similar
but more complete sync solution than L<RT::Authen::ExternalAuth> (which
only updates upon login and doesn't handle groups).  It may be used with
either of RT's external authentication sources, or on it's own.

Starting with RT 4.4, L<RT::LDAPImport> is part of RT. For
earlier versions of RT, you can install L<RT::Extension::LDAPImport> as
an extension.
